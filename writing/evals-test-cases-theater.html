Evals, test cases, and theater.

What makes a test suite good enough? I found a rubric and a rabbit hole.

In my last note I said I do not trust the new tests yet, and I owe the reason. I have seen a test turn green because the agent nullified its purpose (Don’t whitelist errors). So the question I care about is what separates a real test from a staged one, and an insightful answer found me in a working applied-AI engineer’s field guide: evaluate an agent’s output and its behavior separately.

An ideal eval gives an agent a task, lets it run, and grades two things. The outcome: did it produce the correct result. The trajectory: how it behaved getting there, the tools it called, the fields it touched, the actions it attempted. Each gets its own metric, scored and tracked separately. Blend them into one number and the number hides more than it reveals: an agent can ace every answer while occasionally doing something forbidden on the way, and the blended score buries exactly the runs that matter. Report the grades separately or the eval is a performance.

That model grades agents. What I have been building grades code. The regression bench and the CI pipeline live in cleaner territory: deterministic outputs, easily scored. But the agent-grading instincts apply, and the pipeline already writes down what I would need. How many rounds of development before the code passed the test? How often does the verifier have the builder rewrite the code versus having the test author rewrite the test? I can measure that over time, but I have to trust the system before I turn the agents loose to build those trendlines. I need the suite good enough to protect what we have built, and not so heavy that I cannot keep building. So the plan is layers. Basic completeness first, every published page under contract, which is where the bench stands now. Then new categories of test cases for use-cases that cut across pages.

A passing test is only as sound as its author. (Uh oh.)

What the guide really gave me is a rubric I can point at my own architecture. It was written for grading agents, their output and their conduct in a session, and those are questions I already ask by hand every time I review a run. The near-term version is practical: counts the pipeline already records, rounds to green, rewrites ordered, escalations by type, ready to become trendlines once the suite has earned my trust. The sophisticated version, true behavior grading, sits further down the rabbit hole. I plan to descend one measurable step at a time.

Filed under field notes. The two-grades model is Eyad Khrais’s, from his guide to applied AI engineering.

Designing for restraint.

The most dangerous agent is a helpful one, automated.

The lab crossed a line I never saw coming: a guy who had never written code before is now building a suite of regression tests, coded contracts for every page the lab has shipped, with more still coming. Automated quality control, built to run without me. Which raised the real design question: what happens when a check goes red and I am not in the room?

I brought Bond, my QA agent, back from hiatus and gave it teeth: CI checks that can block a merge, and a new job authoring test cases. Instinct, not to mention my history with Bond, said automating QC carried real risk. One failure mode I have seen firsthand is an agent that helps too much. I knew our site worked, essentially, so a new test going red did not necessarily mean broken code. It could mean a suspect test, one that needed review before it earned a place in the suite. An agent allowed to fix whatever it believes is an error, code or test, can compound a real problem or quietly drift the codebase one confident misstep at a time. So the rule is simple: agents never fix a red test before flagging the human. They classify, file a new issue, and stop. I proved the boundary the only way that counts: I planted a failure and let the machinery run. The check went red, and Bond did nothing heroic. It filed the issue in the backlog, then stopped and waited for me. That restraint is not agent virtue. It is the core requirement, met.

Human review already stands at the merge; these guardrails run upstream of it. When building and testing happen at the same time, a verifier agent adjudicates: it halts the loop after five failed passes, so nothing thrashes and no tokens burn, and it halts when the original spec was too thin to decide. Sometimes the outcome is a reworked test. Sometimes the story is marked blocked and waits. Both roads end at the same desk. Mine.

Limiting an agent’s blast radius is a design property, not a hope.

The applied-AI textbooks call this guardrails, routing the high-risk steps to a human. Watching it run felt like something better than theory: a team, myself included, each taking a turn on the line, handing the work along. Fewer human touches, but stronger ones, exactly where the product owner’s decision is owed according to Agile principles. I do not trust these tests yet. I do know we are better with them than without. How much of all that new green is real is the next note’s question.
